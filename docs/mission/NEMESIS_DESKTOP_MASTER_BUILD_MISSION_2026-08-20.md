7.1 Properties targeted for proof
The critical proof obligations should include:
State integrity
	•	Every accepted state transition is valid for the current mission state.
	•	Terminal mission states cannot silently return to running.
	•	A cancelled mission cannot perform new actions.
	•	A completed mission cannot change without creating a new mission or fork.
	•	Sequence numbers increase exactly once per committed event.
	•	Committed events cannot be reordered.
Capability safety
	•	An action cannot execute without a valid capability.
	•	Capabilities may be attenuated but never silently expanded.
	•	A child worker cannot receive more authority than its parent mission permits.
	•	Revoked or expired capabilities cannot authorize actions.
	•	Capability scope must cover the exact resource and operation.
	•	A filesystem capability cannot escape its canonical root.
	•	A network capability cannot silently authorize another host.
	•	A read capability cannot become a write capability.
Budget integrity
	•	Cost, token, time, process, storage, and network budgets never underflow.
	•	A worker cannot allocate more budget than the mission retains.
	•	A child budget is deducted from the parent allocation.
	•	Exhausted budgets cause a typed refusal or approval request.
Approval safety
	•	Approvals bind to the exact normalized action digest.
	•	Approvals are one-shot unless explicitly issued as reusable policy.
	•	Replaying an approval against a modified action fails.
	•	Expired approvals fail closed.
	•	An approval for one mission cannot authorize another mission.
Evidence integrity
	•	Evidence identifies the exact source revision it supports.
	•	A change to a dependent source object invalidates stale evidence.
	•	Evidence cannot support a claim outside its declared scope.
	•	Evidence from an unauthorized verifier cannot satisfy a completion predicate.
	•	Completion requires every mandatory claim to have acceptable, current evidence.
Completion integrity
	•	Workers may only propose completion.
	•	The kernel alone transitions to COMPLETE.
	•	No mission completes while mandatory obligations remain open.
	•	No mission completes using evidence bound to an obsolete source state.
	•	Required human decisions cannot be replaced by an LLM assertion.
	•	A verifier failure cannot be interpreted as a pass.
A representative package contract might look like:
procedure Commit_Action
  (Mission : in out Mission_Record;
   Action  : Action_Request;
   Grant   : Capability_Grant;
   Result  : Action_Result)
with
  Pre  =>
    Mission.State = Running
    and then Authorized (Mission, Action, Grant)
    and then Within_Budget (Mission, Action)
    and then Grant.Status = Active,

  Post =>
    Mission.Sequence = Mission.Sequence'Old + 1
    and then Mission.State /= Complete
    and then Last_Event (Mission).Action_Hash = Digest (Action)
    and then Last_Event (Mission).Capability_Id = Grant.Id;
The kernel should have a declared trusted-computing-base budget. Any package added to the TCB requires an RFC explaining why the invariant cannot live outside it.

11. Consequence-aware assurance
Every claim and action receives a structured consequence class.
Consequence	Example	Minimum assurance
Informational	Summarize a file	Source citation or direct observation
Advisory	Recommend a refactor	Evidence plus uncertainty
Decision-boundary	Decide whether a release is ready	Deterministic checks and independent review
Safety-critical	Modify authorization or cryptographic boundaries	Strong deterministic verification, human approval, and elevated policy
This must not be a free-form model-written field. The kernel owns the permitted classes and the evidence policy associated with each class.
An LLM review can be evidence for an informational or advisory claim. It cannot be the sole evidence for a safety-critical completion claim.

17. Completion belongs to the kernel
The worker protocol contains:
PROPOSE_COMPLETION
It does not contain:
COMPLETE
The completion engine evaluates:
For every required completion claim:
    claim exists
    evidence exists
    evidence is accepted
    evidence is fresh
    evidence is bound to the current source state
    verifier is authorized for the consequence class
    no conflicting blocker remains unresolved
Only then:
VERIFYING → COMPLETE
Otherwise:
VERIFYING → RUNNING
or:
VERIFYING → BLOCKED_WITH_EVIDENCE
The final model response is not the mission verdict.
The mission verdict is a kernel state transition.

26. Security architecture
The threat model must assume:
	•	A model may be wrong.
	•	A model may be manipulated by repository content.
	•	A model may intentionally attempt to exceed authority.
	•	A plugin may be malicious.
	•	An MCP server may be compromised.
	•	A remote provider may return adversarial content.
	•	A repository may contain prompt injection.
	•	A build script may attempt secret extraction.
	•	A worker may fabricate tool output.
	•	A tool may return malformed data.
	•	An approval may be replayed.
	•	A path may contain symlink or traversal attacks.
	•	A dependency may be compromised.
	•	A daemon may crash at any state transition.
	•	A frontend may be compromised.
	•	A receipt signer may be unavailable.
26.1 Secret broker
Secrets never enter every worker’s inherited environment.
A worker requests:
Request credential:
  provider: GitHub
  purpose: read checks for PR 81
  scope: repo:owner/repo
  operations: checks:read
  expiry: 10 minutes
The broker returns either:
	•	A short-lived scoped token
	•	A proxied operation
	•	A refusal
	•	A request for human approval
Long-lived credentials remain in the OS keychain or external secret manager.
26.2 Network broker
Network access is expressed by:
	•	Host
	•	Port
	•	Protocol
	•	Method
	•	Path scope
	•	Rate
	•	Data classification
	•	Expiration
A capability for api.github.com does not imply unrestricted internet access.
26.3 Filesystem broker
All paths undergo:
	•	Canonicalization
	•	Root comparison
	•	Symlink resolution
	•	Mount-boundary policy
	•	Special-file rejection
	•	Race-resistant opening where supported
26.4 Sandbox profiles
Profiles include:
Profile	Behavior
Observe	No mutation
Workspace Safe	Writes only within an isolated worktree
Container	Worker runs in a restricted container
VM	Worker runs in a disposable VM
Remote	Worker executes on a separate controlled host
Privileged Local	Explicitly authorized exceptional access
Failing to establish the requested sandbox must not silently fall back to a weaker profile.
 
⸻

UI API
	•	OpenAPI 3.1
	•	JSON request/response
	•	WebSocket event stream

34. Claims the project must not make
Trust will depend as much on restraint as capability.
Do not claim:
	•	“SESHAT makes LLMs correct.”
	•	“Every part of SESHAT is formally verified.”
	•	“A signed receipt proves the real-world claim is universally true.”
	•	“Replay means a nondeterministic model will reproduce the same answer.”
	•	“Sandboxing makes arbitrary code perfectly safe.”
	•	“An LLM reviewer is independent proof.”
	•	“Open source means model APIs cost nothing.”
	•	“GNATprove passing means external libraries are correct.”
	•	“A secure kernel eliminates all supply-chain risk.”
The honest claim is:
SESHAT constrains authority, records causality, evaluates explicit completion predicates, and produces independently checkable evidence for the properties its verifiers are qualified to establish.
That is already a major leap.

37. The precise strategic position
Do not market SESHAT as:
“A better AI coding assistant.”
Market it as:
An open operating system for witnessed autonomy.
Hermes is excellent at giving agents reach: many providers, tools, platforms, skills, execution environments, and front ends.
SESHAT’s reason to exist is different:
	•	Durable missions instead of fragile sessions
	•	Formal authority instead of prompt obedience
	•	Typed capabilities instead of ambient tools
	•	Evidence graphs instead of confident summaries
	•	Verifier-owned completion instead of model-owned completion
	•	Sandboxed plugins instead of full renderer authority
	•	Context compilation instead of context accumulation
	•	Causal replay instead of retrospective storytelling
	•	Signed mission receipts instead of “trust me, I ran it”
The revolutionary center remains:
Intelligence proposes. The kernel disposes. Evidence decides.
And the final product promise remains:
The AI is probabilistic. The authority governing the AI is not.
The correct first implementation move is now Phase 0 and RFC-0001—locking this constitution, the trust boundaries, the threat model, and the first vertical-slice acceptance test before anyone writes the large application shell.
